# Multi-Service Diagnostic Bundle Implementation Reference

## 1. Problem

The Observability diagnostic export is generated by the public `api` process.
It can read shared PostgreSQL records, selected-character messages, messaging
receipts, delivery rows, and referenced storage metadata, but it cannot prove
the runtime state of the dedicated `coordinator`, `worker`, and `connector`
processes.

The current `deployment` block identifies only the API instance that created
the ZIP. When `include_logs=true`, `application_logs.jsonl` contains only the
bounded in-memory WARN/ERROR buffer of that API process. Zeabur build failures,
Pod lifecycle events, probes, OOM events, and the other services' process-local
logs remain outside the bundle.

## 2. Goal

Add a bounded, redacted fleet snapshot to the existing admin-only diagnostic
ZIP so an operator can distinguish:

- an API incident from a coordinator, worker, or connector incident;
- shared durable state from process-local observations;
- a healthy running deployment from historical Zeabur build failures;
- durable worker readiness from durable acceptance or frontend rollout state.

This extension must remain read-only and must not require a Zeabur management
token inside any application service.

## 3. Security Boundary

- Do not place `ZEABUR_TOKEN`, Git credentials, database credentials, JWT
  secrets, connector tokens, or provider keys in application configuration or
  exported artifacts.
- Do not let the API invoke Zeabur mutations, restart services, or fetch broad
  platform logs while producing a diagnostic bundle.
- Keep the endpoint admin-only, `Cache-Control: no-store`, limited to a 24-hour
  window, and subject to existing row, text, and object caps.
- Preserve mandatory redaction for secret-shaped keys and values, including in
  new fleet fields.
- Treat service health reports and heartbeats as observations. They do not
  override PostgreSQL command, lease, or effect state.

## 4. Proposed Architecture

Each process publishes a small non-sensitive heartbeat row to PostgreSQL. The
API reads these rows when producing a bundle. This avoids private-network HTTP
fan-out from the request handler and works when a process is unavailable.

Suggested table: `runtime_process_heartbeats`.

| Field | Purpose |
| --- | --- |
| `instance_id` | Stable identity for one process incarnation |
| `process_role` | `api`, `coordinator`, `worker`, or `connector` |
| `service_name` | Optional deployment label, never a credential |
| `build_commit_sha` / `build_tag` | Source/image identity |
| `started_at` / `last_seen_at` | Restart and freshness evidence |
| `health_state` | Bounded `starting`, `healthy`, `degraded`, `stopping` value |
| `durable_acceptance_enabled` | API flag observation |
| `durable_worker_enabled` / `durable_worker_alive` | Worker configuration and loop liveness |
| `background_coordinator_alive` | Coordinator loop liveness |
| `connector_runtime_state` | Bounded connector state summary |
| `details_json` | Versioned, allow-listed counters only |

The heartbeat writer must update one row per live incarnation at a conservative
interval and stop on graceful shutdown. Rows are not deleted immediately;
staleness explains missing processes after a crash. Add bounded retention for
old incarnations after incident windows have elapsed.

## 5. Bundle Contract

Add `fleet_status.json` and a summary block in `incident_summary.json`.

```json
{
  "schema_version": 1,
  "observed_at": "2026-09-20T00:00:00Z",
  "expected_roles": ["api", "coordinator", "worker", "connector"],
  "roles": [],
  "coordinator_lease": {},
  "durable_chat": {},
  "background_queue": {},
  "coverage": {}
}
```

Each role entry should include only process identity, build identity, start and
last-seen timestamps, freshness, and allow-listed liveness/counter fields.
`coverage` must say whether the snapshot is complete, partial, stale, or
unavailable and why.

The durable section should report aggregate counts by command/effect state,
oldest active command age, and worker heartbeat freshness. It must not export
command payload JSON, chat text, generated snapshots, provider responses, or
billing secrets.

The coordinator section should include the current lease owner, fencing epoch,
lease deadline, and whether it is live at snapshot time. Queue information
should remain aggregate counts and oldest age.

The connector section should use durable messaging account/receipt/delivery
state plus heartbeat freshness. It must not export connector credentials or
pretend that a recent receipt proves the process is currently alive.

## 6. Platform Evidence

Zeabur deployment/build/runtime events remain an external evidence source.
The ZIP should include a manifest slot such as
`external_platform_evidence.status = "not_included"` and explain that platform
events must be downloaded separately or attached by an operator.

A future privileged diagnostic collector may merge a separately supplied,
redacted Zeabur export. It must run outside the application trust boundary and
must not expose a platform mutation credential to the API process.

## 7. UI Changes

- Keep the current Quick, Standard, and Full presets.
- Include the fleet snapshot in every preset because it is bounded and contains
  no chat text.
- In Full, retain the current opt-in API-process logs and storage metadata.
- Label application logs as `API process logs` until multi-process log
  collection exists.
- After download, show the `X-Diagnostic-Completeness` result and list missing
  or stale roles without claiming the whole application is unhealthy.

## 8. Verification

1. Four healthy roles produce four fresh entries with the same deployed SHA.
2. Stopping one role leaves a stale, identifiable entry rather than silently
   omitting it.
3. Rolling deployment can show old and new incarnations without reporting two
   active owners when only one lease is live.
4. Coordinator lease owner/epoch matches the database lease row.
5. Durable worker enabled/alive is reported only by the worker role.
6. Acceptance and frontend rollout flags remain distinct from worker readiness.
7. Aggregate durable command/effect counts match direct read-only SQL.
8. Connector credentials, JWT/database/provider secrets, prompts, messages,
   and command payloads never appear in the fleet files.
9. Missing heartbeat table or partial migration returns a useful partial ZIP,
   not HTTP 500.
10. Existing diagnostic ZIP and frontend tests continue to pass.

## 9. Implementation Slices

- **D1 contract and migration:** heartbeat model/repository, additive migration,
  retention rule, redaction schema, and PostgreSQL tests.
- **D2 process publishers:** role-aware heartbeat/liveness publisher wired into
  `api`, `coordinator`, `worker`, and `connector` startup/shutdown.
- **D3 export:** fleet reader, aggregate durable/queue/lease queries,
  `fleet_status.json`, summary coverage, and ZIP regression tests.
- **D4 UI:** clarify process-local logs, expose fleet completeness, and update
  Traditional Chinese, English, and Japanese strings.
- **D5 deployment:** isolated four-role rehearsal, additive Prod migration,
  same-SHA rollout, one-role-stop test, and final evidence update.
